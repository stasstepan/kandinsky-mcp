# Архитектура

MCP-сервер, который даёт агенту генерацию изображений через Kandinsky API.
Один образ, два транспорта, файлы сохраняются на сервере и отдаются ссылкой.

## 1. Задача

API Kandinsky асинхронный: заявка создаётся, считается воркером, забирается
отдельным запросом.

```
POST /tasks/<route>     → task_id
GET  /tasks/{id}        → queued | processing | done | failed
GET  /tasks/{id}/result → бинарный файл
```

Из этой схемы следуют четыре ограничения, которые определяют всю архитектуру.

| Ограничение | Последствие |
|---|---|
| Результат **одноразовый**: 10 минут на скачивание, после скачивания живёт 60 секунд, повторная выдача → 422 | файл нужно забирать сразу и хранить у себя |
| Задача живёт 45 минут, потом API её роняет | ждать результат нужно дольше, чем длится один вызов инструмента |
| Квоты: на маршрут (сутки/месяц), не более **двух** параллельных задач, минимальный интервал между запросами | повторы и параллельные дубли стоят дорого |
| У MCP-клиента свой таймаут на вызов инструмента — обычно 60 секунд | нельзя блокировать вызов дольше этого времени |

## 2. Решения

**Сервер работает как менеджер задач, а не как обёртка над HTTP.** Задачу
сопровождает фоновый поллер: опрашивает API, ловит `done`, один раз скачивает
файл и кладёт на диск. Агент в любой момент видит согласованное локальное
состояние, а ограничение «10 минут» перестаёт что-либо значить.

**Контракт инструментов асинхронный.** `kandinsky_image_generate` создаёт задачу
и ждёт результат не дольше 45 секунд. Не успело — возвращается `task_id`, а файл
забирается позже через `kandinsky_task_result`. Тот читает диск и в API не ходит,
поэтому его можно вызывать сколько угодно раз.

**Защита от повторов.** Если точно такой же запрос уже выполняется, сервер
возвращает существующую задачу вместо новой. Окно в 90 секунд дополнительно
покрывает повторы после завершения. Обойти можно параметром `force_new`.

**Доставка файла тремя способами.** Подписанная ссылка (основной путь),
inline-превью картинки в ответе инструмента (до 1.5 МБ) и base64 по запросу
(до 4 МБ). Ссылка защищена подписью, а не ключом доступа: агент скачивает файл
обычным GET без заголовков.

## 3. Слои

```
┌───────────────────────────────────────────────────────────┐
│ tools/    инструменты MCP: схемы, валидация, тексты ошибок │
├───────────────────────────────────────────────────────────┤
│ domain/   tasks   — поллеры, состояние, восстановление     │
│           store   — файлы задач и результатов, TTL         │
│           media   — проверка и ресайз входных картинок     │
├───────────────────────────────────────────────────────────┤
│ api/      client  — httpx, Bearer, ретраи, 429             │
│           routes  — реестр маршрутов, сверка с openapi      │
│           errors  — коды API → доменные ошибки             │
├───────────────────────────────────────────────────────────┤
│ auth, http_app, config, server — обвязка                   │
└───────────────────────────────────────────────────────────┘
```

Разделение позволяет тестировать каждый слой отдельно: клиент — на моках HTTP,
менеджер задач — на скриптованном фейке API, инструменты — без сети.

## 4. Жизненный цикл задачи

```
create ──► POST /tasks/…  ──► task_id
              │
              ├──► /data/tasks/<id>.json   (метаданные, атомарная запись)
              └──► фоновый поллер
                        │
                        ├─ GET /tasks/{id} раз в 2–10 секунд (бэкофф);
                        │  квота на чтение не расходуется
                        ├─ done   → GET /tasks/{id}/result — ровно один раз
                        │           → /data/results/<дата>/<id>.<ext> + sha256
                        └─ failed → сохранить причину, задача терминальна
```

Состояния: `queued → processing → saved | failed`.

После рестарта контейнера состояние восстанавливается из `/data/tasks/*.json`,
поллеры для незавершённых задач перезапускаются. Скачивание защищено блокировкой
на задачу: поллер и ручной запрос результата не могут скачать файл дважды.

## 5. Транспорты

| Режим | Запуск | Назначение |
|---|---|---|
| `http` | uvicorn на `MCP_HTTP_PORT`, `POST /mcp` | постоянный сервис за реверс-прокси |
| `stdio` | `python -m kandinsky_mcp` | локальный запуск агентом как подпроцесса |

Режим выбирается переменной `MCP_TRANSPORT`. HTTP-эндпоинты:

| Путь | Доступ | Назначение |
|---|---|---|
| `POST /mcp` | ключ доступа | MCP Streamable HTTP |
| `GET /files/<path>?exp=&sig=` | подпись в URL | готовые изображения |
| `GET /stats` | ключ доступа | расход по маршрутам за месяц |
| `GET /healthz` | публичный | живость процесса |
| `GET /readyz` | публичный | доступность Kandinsky API, кеш 30 с |

## 6. Реестр маршрутов

Маршрут описан данными: допустимые параметры, значения перечислений, лимиты
входа, тип результата. Инструменты работают через реестр, поэтому новый маршрут
добавляется записью, а не правкой каждого инструмента.

При старте сервер запрашивает `GET /openapi.json` и сверяет реестр с фактом:

- маршрут есть в реестре, но отсутствует в API → помечается недоступным;
- в API появился маршрут, которого нет в реестре → запись в лог;
- расхождение в перечислениях → предупреждение.

Сверка не роняет сервер: разные инсталляции API отличаются набором маршрутов,
и это нормальная ситуация, а не сбой. Недоступные маршруты исчезают из справки
`kandinsky_routes`, а их инструменты отвечают понятной ошибкой.

## 7. Ответ инструментов

Единый формат для всех инструментов:

```json
{
  "task_id": "1842",
  "status": "saved",
  "model": "k6-image-t2i",
  "prompt": "закат над морем",
  "params": {"query": "закат над морем", "resolution": "1024x1024"},
  "elapsed_ms": 18400,
  "media": [{
    "mime": "image/jpeg",
    "bytes": 1482311,
    "sha256": "9f2c…",
    "url": "https://host/files/results/2026-02-14/1842.jpg?exp=…&sig=…",
    "path": "results/2026-02-14/1842.jpg"
  }],
  "next": "Файл сохранён. Ссылка media[].url отдаёт его по подписи."
}
```

`next` содержит подсказку, что делать дальше: забрать файл, подождать или
исправить запрос. Ошибки возвращаются с `is_error: true` и кодом, по которому
можно действовать.

## 8. Ошибки

Коды API переводятся в доменные: агент видит не «HTTP 422», а причину и рецепт.

| Ответ API | Код | Что делать агенту |
|---|---|---|
| 401 / 403 | `auth_failed` | проверить токен (настройка сервера) |
| 404 | `not_found` | задача неизвестна этому серверу |
| 413 | `input_too_large` | уменьшить входной файл |
| 422 `too big resolution` | `input_bad_resolution` | уменьшить стороны картинки |
| 422 `prompt too long` | `prompt_too_long` | сократить промпт |
| 422 `blocked by censor` | `censored` | переписать промпт, повтор бесполезен |
| 422 `censor unavailable` | `censor_unavailable` | повторить позже |
| 422 `not ready` | `not_ready` | подождать завершения |
| 422 `already delivered` | `result_gone` | нужна новая генерация |
| 429 `daily` / `monthly` | `quota_daily` / `quota_monthly` | ждать сброса квоты |
| 429 `concurrent` | `quota_concurrent` | дождаться завершения запущенных задач |
| 429 `rate` | `quota_rate` | подождать интервал |
| 5xx, сеть | `upstream_error` / `network_error` | повторить |

Ретраи выполняются только для идемпотентных запросов и для создания задачи,
пока не получен `task_id`. Ответ 429 несёт структурированные поля `used` и
`limit` — они сохраняются и показываются в `/stats`, потому что отдельного
метода для остатка квоты в API нет.

## 9. Безопасность

- токен API живёт только в окружении, в логи и ответы не попадает;
- MCP-эндпоинт требует ключ: заголовок `X-API-Key`, `Authorization: Bearer`
  или ключ в произвольном заголовке — некоторые клиенты не умеют иначе;
- ссылки на файлы подписаны HMAC и имеют срок; каталог данных целиком не отдаётся;
- в HTTP-режиме запрещено читать локальные пути: иначе ключ доступа превращался
  бы в право прочитать любой файл сервера. Своё хранилище при этом доступно —
  по `path` из ответа или по своей же ссылке;
- ограничение частоты запросов защищает дневную квоту API;
- контейнер работает не от root, корневая файловая система только для чтения,
  запись — единственный том с данными.

## 10. Наблюдаемость

- структурированные логи в stdout: время, уровень, компонент, `task_id`, маршрут;
- `/healthz` — процесс жив, `/readyz` — API Kandinsky доступен;
- `/stats` — расход по маршрутам за текущий месяц, последняя ошибка и сведения
  о квоте из ответа 429;
- предупреждения в логе при расхождениях с API и при подмене формата файла.

## 11. Хранилище

```
/data
  tasks/<task_id>.json                   состояние, параметры, ошибки, файлы
  results/<YYYY-MM-DD>/<task_id>.<ext>   готовые изображения
  quota.json                             последние used/limit из ответов 429
```

Запись атомарная: временный файл и переименование. Срок хранения результатов
задаётся `RESULT_TTL_HOURS`, уборка запускается раз в час.

## 12. Ограничения

- только изображения: генерация по тексту, редактирование по картинке,
  увеличение разрешения. Видео, видео со звуком и аватар в API есть, но
  инструментов под них нет;
- одна учётная запись API на сервер, без мультипользовательского режима;
- входные изображения принимаются как base64, data-URI или путь в своём
  хранилище; загрузка по внешнему URL отключена.

## 13. Точки расширения

Реестр уже содержит описания видеомаршрутов (`k5_video_t2v_*`, `k5-i2v-*`,
`k6_t2va_lite`, `giga_avatar`) с пометкой «инструмент не опубликован». Чтобы
добавить видео, достаточно трёх инструментов и проверки формата результата —
ядро, хранилище и доставка файлов не меняются.
