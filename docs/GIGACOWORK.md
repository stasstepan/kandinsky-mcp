# GigaCowork

Как Kandinsky MCP подключается к [GigaCowork](https://cowork.ru): адрес,
транспорт, авторизация, файлы сессии, лимиты и порядок регистрации. Всё
остальное об устройстве сервера — в [README](../README.md) и
[ARCHITECTURE](ARCHITECTURE.md).

Ниже — целевой контракт профиля GigaCowork (руководство «Разработка внешнего
MCP для GigaCowork», версия MCP `2025-11-25`). Фактическое состояние
конкретного адреса проверяется скриптом
[scripts/compat_check.py](../scripts/compat_check.py), а не этим текстом.

Артефакты для регистрации лежат рядом:

| Файл | Что это |
|---|---|
| [gigacowork/definition.yaml](../gigacowork/definition.yaml) | Definition интеграции (`cowork-proxy-definition/v2`, `id: kandinsky-image`) |
| [gigacowork/integration.yaml](../gigacowork/integration.yaml) | Минимальная карточка витрины `cowork_hub` |
| [scripts/compat_check.py](../scripts/compat_check.py) | Проверка совместимости по сценарию §3.9 |

## 1. Что делает интеграция

Kandinsky MCP — удалённый MCP-сервер для работы с изображениями через
Kandinsky API. Агенту доступны семь инструментов:

| Инструмент | Назначение | Меняет данные |
|---|---|---|
| `kandinsky_image_generate` | изображение по текстовому описанию (модель `k6` или `k5`, разрешение, `beautificator`, `censor`) | да |
| `kandinsky_image_edit` | изменение картинки по описанию (1–3 входных изображения) | да |
| `kandinsky_image_upscale` | увеличение ×2 или ×4 (super resolution) | да |
| `kandinsky_task_status` | состояние задачи (`queued`/`processing`/`saved`/`failed`) | нет |
| `kandinsky_task_result` | готовый файл: ссылка, размер, sha256, превью; в API не ходит | нет |
| `kandinsky_tasks_list` | последние задачи с фильтрами | нет |
| `kandinsky_routes` | бесплатная справка по маршрутам, моделям и параметрам | нет |

Имена удовлетворяют `[A-Za-z0-9_-]{1,64}` и уникальны; весь каталог приходит
в первом ответе `tools/list` без пагинации. Инструменты чтения помечены
`readOnlyHint`, изменяющие — `destructiveHint=false`, `openWorldHint=true`.
Ответ каждого инструмента — короткая текстовая сводка и `structuredContent`
с машинно-читаемыми полями (см. [README, «Инструменты»](../README.md#инструменты)).

Генерация асинхронная: инструмент ждёт готовности не дольше 45 секунд, а если
не успел — возвращает `task_id`; файл забирается позже через
`kandinsky_task_result` и не тратит квоту повторно.

## 2. Адрес и транспорт

- Канонический адрес: **https://kandinsky.stasstep.ru/mcp** (порт 443).
- Транспорт: **Streamable HTTP**; stdio-режим GigaCowork не используется.
- Версия протокола: **2025-11-25**. Версия `2026-07-28` в профиль не входит и
  сервером не объявляется.
- TLS-сертификат соответствует имени хоста и строит полную цепочку до
  доверенного публичного удостоверяющего центра.
- Каждое JSON-RPC-сообщение — отдельный `POST` с
  `Content-Type: application/json` и
  `Accept: application/json, text/event-stream`; ответ приходит как
  `application/json` или как SSE (`text/event-stream`, JSON-RPC-документы в
  строках `data:`), ровно один `result`/`error` на исходный `id`.
- `initialize` возвращает `MCP-Session-Id`; тот же заголовок принимается во
  всех запросах сессии. После согласования версии сервер принимает
  `MCP-Protocol-Version: 2025-11-25`.
- `GET /mcp` без сессии — `405 Method Not Allowed` (`Allow: POST, DELETE`);
  с сессией — штатный SSE-поток SDK.
- Запрос с незнакомым `Origin` отклоняется `403 Forbidden`; разрешённые
  источники задаются переменной `MCP_ALLOWED_ORIGINS` (по умолчанию список
  пуст, то есть любой присланный `Origin` считается недоверенным).

Адрес MCP **не записывается в Definition**: он связывается с интеграцией при
регистрации. Если когда-нибудь понадобится выбирать адрес в подключении, для
этого есть несекретное поле `upstream.endpoint` типа `url` (§2.4.6
руководства); сейчас оно не используется.

## 3. Авторизация

- Способ доступа: **пользовательские HTTP-заголовки** (`custom_headers`).
- Заголовок: **`X-API-Key`**, значение — ключ доступа сервера (переменная
  `MCP_API_KEY` на стороне сервера). Сервер принимает также
  `Authorization: Bearer <ключ>`, но для GigaCowork используется `X-API-Key`.
- `allow_shared_account: true`: ключ можно один раз настроить на организацию
  (общее подключение) или выдавать индивидуально. Ограничение общее для всех
  режимов — квота Kandinsky API привязана к ключу сервера.
- Запрос без ключа или с неверным ключом — `401 Unauthorized`.
- OAuth не поддерживается: метаданные защищённого ресурса и сервера
  авторизации не публикуются, `redirect_uri` не нужен. Ротация ключа —
  ручная: новый ключ вводится в подключении.
- Токен Kandinsky API и значение ключа не попадают в ответы инструментов,
  тексты ошибок и журналы.

Definition с полем `api_key` и передачей в `X-API-Key` —
[gigacowork/definition.yaml](../gigacowork/definition.yaml); секретов в нём нет.

## 4. Файлы сессии

Платформа передаёт файлы не через JSON-аргументы, а через временные адресные
ссылки, и только если инструмент явно объявил расширение `x-session-file-*`.

### 4.1. Входной файл: `read_url`

`kandinsky_image_edit` и `kandinsky_image_upscale` объявляют технический
аргумент `read_url`:

```json
"read_url": {
  "type": "string",
  "x-session-file-input": {"model_field": "source", "transport": "read_url"}
}
```

- Агент видит поле выбора файла сессии `source`, а не URL; `read_url`
  подставляет GigaCowork перед вызовом.
- Сервер скачивает файл по HTTPS методом `GET` в пределах одного вызова,
  проверяет размер, при необходимости уменьшает картинку под лимиты маршрута
  и использует как вход. URL не логируется и не сохраняется.
- `images`/`image` становятся необязательными; если не передан ни один
  источник, инструмент возвращает `isError: true` с понятным текстом.
- Лимиты Kandinsky API строже платформенных: входное изображение ≤ 25 МБ и
  ≤ 2048 px, для super resolution — ≤ 4 МБ и ≤ 1024 px. Сервер уменьшает
  картинку автоматически и сообщает об этом в `warnings`.

### 4.2. Выходной файл: `x-session-file-output: url`

`kandinsky_image_generate`, `kandinsky_image_edit`,
`kandinsky_image_upscale` и `kandinsky_task_result` объявляют аннотацию
`annotations: {"x-session-file-output": "url"}`. Когда файл готов, сервер
возвращает в `structuredContent`:

| Поле | Смысл |
|---|---|
| `filename` | безопасное имя файла, например `14495.jpg` (имя = `<task_id>.<ext>`) |
| `content_type` | MIME-тип сохранённого файла (`image/png`, `image/jpeg`) |
| `download_url` | подписанная HTTPS-ссылка на `/files/...`, порт 443 |
| `size` | размер файла в байтах |

Файл объявляется по §5.3: пока он готов, в `structuredContent` есть
`filename`, `content_type`, `download_url`, `size`, а `download_url` отдаётся
без сжатия (`Content-Encoding: identity`). Пока файла нет
(`status=queued`/`processing`), полей файла нет: инструмент не сообщает об
успехе раньше времени.

**Практика (проверено на живом GigaCowork):** платформа не запрашивает
`download_url` и не переносит файл в сессию (в логах Caddy — ни одного GET
`/files/...` после генерации). Поэтому:

- `download_url` дублируется строкой в `content[].text`, чтобы агент мог отдать
  ссылку пользователю (осознанное отступление от §1.1: иначе файл недоступен);
- inline-превью не режется бюджетом (`MAX_INLINE_RESULT_CHARS=0`): только из
  MCP image-блока GigaCowork показывает картинку в чате;
- аннотация `x-session-file-output` остаётся — для платформ/версий, которые
  файловый режим поддерживают.

### 4.3. Лимиты файлов

| Область | Значение по умолчанию | Правило |
|---|---|---|
| Один входной или выходной файл | 100 MiB | файл сверх лимита отклоняется |
| Все входные файлы одного вызова | 200 MiB | считается суммарно до выдачи временных адресов |
| Передача файла | 120 с | включает скачивание или загрузку |
| Имя выходного файла | 1–255 байт UTF-8 | без `/`, `\`, NUL, управляющих символов, `.`/`..` и ведущей точки |
| `download_url` | HTTPS, порт 443 | без встроенных учётных данных; перенаправления проверяются повторно |

### 4.4. Безопасность временных ссылок

Временный адрес — разрешение на один файл. Сервер использует его только в
текущем вызове, не пишет полный URL в журнал, не сохраняет в базе или
аналитике, не возвращает в `content`, `structuredContent` и тексте ошибки и
не добавляет к URL своих параметров. Передача завершается до окончания вызова.

## 5. Ограничения GigaCowork и параметры Definition

Значения платформы — настройки по умолчанию, для конкретной установки они
могут быть уменьшены.

| Класс | Ограничение |
|---|---|
| Предварительная проверка адреса | 5 с на весь начальный обмен; до 256 KiB на ответ |
| Обновление списка инструментов | 30 с; до 10 MiB на один MCP-ответ |
| Запуск MCP-подключения | 20 с |
| Один `tools/call` | 60 с |
| Результат одного инструмента | 100 000 символов |
| Схемы инструментов в одном ходе агента | до 24 активных |

Наши значения в [Definition](../gigacowork/definition.yaml):

| Поле | Значение | Почему |
|---|---|---|
| `runtime.request_timeout_ms` | `55000` | укладывается в 60 с платформы; генерация ждёт до 45 с и возвращает `task_id`, если не успела |
| `runtime.max_response_bytes` | `10485760` | 10 MiB — лимит одного MCP-ответа в GigaCowork |
| `runtime.forward_client_headers` | `[]` | серверу не нужны клиентские заголовки |
| `configuration.fields` | `[]` | несекретных настроек нет |

Сервер отвечает раньше клиентского таймаута: общий бюджет `CALL_BUDGET_SECONDS`
(45 с) отсчитывается от начала вызова вместе с созданием задачи. `wait_seconds`
больше бюджета — не ошибка: ожидание обрезается, а если результат не готов,
возвращается `task_id` (его забирают через `kandinsky_task_result`). Это важно:
на живом запросе модель GigaCowork передала `wait_seconds=90`, старый сервер
ответил `-32602`, и платформа показала «Internal error».

## 6. Уровни ошибок

| Уровень | Когда | Пример |
|---|---|---|
| HTTP | TLS, сеть, доступ до разбора JSON-RPC | `401` без/с неверным `X-API-Key`, `403` чужой `Origin`, `405` `GET /mcp` без сессии, `429` превышение `RATE_LIMIT_PER_MINUTE` (по умолчанию 120/мин), `5xx` |
| JSON-RPC error | JSON-RPC разобран, но вызов структурно некорректен | неизвестный инструмент и невалидные аргументы — `-32602` «Invalid tool arguments»; без деталей pydantic и значений |
| Результат с `isError: true` | инструмент найден и вызван, прикладная операция не удалась | исчерпана квота, Kandinsky API недоступен, нечитаемая входная картинка; понятный текст в `content` |

В `message`, `content`, `structuredContent` и диагностике не бывает токенов,
паролей, временных файловых URL, внутренней трассировки стека.

## 7. Чек-лист регистрации (§2.5)

Пакет для регистрации передаётся по согласованному каналу — публичного API
для самостоятельной публикации Definition нет.

| Материал | Что предоставляем |
|---|---|
| MCP-сервер | канонический адрес `https://kandinsky.stasstep.ru/mcp`, профиль `2025-11-25`, Streamable HTTP, результат проверки `initialize → tools/list → tools/call` (вывод `scripts/compat_check.py`), тестовый период доступности — уточнить (см. открытые вопросы) |
| Инструменты | имена, назначения, JSON Schema и `outputSchema`, изменяющие операции, ожидаемые ошибки и примеры результата; фактический каталог публикует сам сервер в `tools/list`, описание — в [README](../README.md), текст — в [api-reference.md](api-reference.md) |
| Авторизация | `custom_headers`, заголовок `X-API-Key`; индивидуальный и общий режим, `allow_shared_account: true`; OAuth, scope и `redirect_uri` не применяются |
| Definition | [gigacowork/definition.yaml](../gigacowork/definition.yaml) без секретов |
| Карточка витрины | slug `kandinsky-image`, [gigacowork/integration.yaml](../gigacowork/integration.yaml), изменение в `cowork_hub` — открытый вопрос |
| Эксплуатационные параметры | ограничение частоты `RATE_LIMIT_PER_MINUTE` (120/мин по умолчанию), типичная и максимальная длительность вызова (до 45 с ожидания, лимит запроса 55 с), размеры ответов, контакт для эксплуатационных обращений — уточнить (см. открытые вопросы) |

Что проверяется при регистрации (§2.6):

1. HTTPS-адрес доступен из контура GigaCowork, сертификат соответствует хосту
   и выдан доверенным публичным центром.
2. MCP согласует поддерживаемую версию и проходит полный жизненный цикл.
3. Первый `tools/list` содержит обязательные инструменты, имена и схемы проходят
   ограничения GigaCowork.
4. Definition не содержит секретов, ссылки `source` и назначения корректны,
   выбранный способ авторизации согласован.
5. Карточка (если нужна) содержит только разрешённые поля и использует тот же
   идентификатор.
6. Положительные и отрицательные `tools/call` дают ожидаемые результаты и ошибки.
7. Файловые инструменты проходят отдельную проверку размера, имени и передачи файла.

## 8. Проверка совместимости

Скрипт [scripts/compat_check.py](../scripts/compat_check.py) повторяет сценарий
§3.9 руководства и печатает `PASS`/`FAIL` по каждому пункту.

```powershell
# PowerShell
$env:MCP_API_KEY = '<ключ доступа>'
python scripts/compat_check.py            # MCP_URL по умолчанию
```

```bash
# bash
MCP_API_KEY='<ключ доступа>' python scripts/compat_check.py
```

Переменные окружения: `MCP_URL` (по умолчанию
`https://kandinsky.stasstep.ru/mcp`) и `MCP_API_KEY`; ключ в код не
захардкожен и не печатается.

Что проверяется:

- `initialize`: HTTP 2xx, `Content-Type: application/json` или
  `text/event-stream`, ответ с исходным `id`,
  `result.protocolVersion == "2025-11-25"`, заголовок `MCP-Session-Id`;
- `notifications/initialized`: `202` или другой 2xx;
- `tools/list`: исходный `id`, все семь обязательных инструментов в первом
  ответе, имена по `[A-Za-z0-9_-]{1,64}`, без дублей и без пагинации;
- `tools/call` бесплатного `kandinsky_routes` с `{}`: `id`, `result`,
  `structuredContent`, `isError` отсутствует;
- негативные кейсы: неизвестный инструмент → JSON-RPC error `-32602`,
  `kandinsky_task_status` без `task_id` → `-32602`, `GET /mcp` без сессии →
  `405`, `POST` с `Origin: https://evil.example` → `403`, неверный
  `X-API-Key` → `401`;
- закрытие сессии `DELETE /mcp` → `200`/`202`/`204`.

Квота Kandinsky API не расходуется: из инструментов вызывается только
бесплатная справка `kandinsky_routes`, остальные вызовы отклоняются сервером
до обращения к API.

Коды возврата: `0` — все проверки прошли, `1` — есть `FAIL`, `2` — ошибка
конфигурации или сети (нет `MCP_API_KEY`, адрес недоступен, ключ отклонён).

## 9. Открытые вопросы

1. **Форма `custom_headers`.** В §2.4.4 руководства приведено только назначение
   метода. В [definition.yaml](../gigacowork/definition.yaml) — компактный
   вариант `fields` + `delivery` (поле `api_key` → заголовок `X-API-Key`);
   подтвердить при регистрации.
2. **Идентификатор категории витрины.** В [integration.yaml](../gigacowork/integration.yaml)
   стоит `category: creative`; точное значение берётся из `categories.yaml`
   репозитория `cowork_hub`. Пропущено по решению владельца интеграции.
3. **Идентификатор карточки.** Карточка содержит четыре поля §2.3, id задаётся
   slug папки `integrations/kandinsky-image` и совпадает с `Definition.id`.
   Сверить с README `cowork_hub` при добавлении карточки.
4. **Канал передачи пакета регистрации.** Публичного API нет; передать через
   согласованный канал проекта. Контакт владельца — репозиторий
   `stasstepan/kandinsky-mcp` (issues/PR).
5. **Тестовый период доступности.** Сервис работает постоянно; для регистрации
   согласовать окно проверки с командой GigaCowork.
6. **OAuth.** Не поддерживается: авторизация остаётся `X-API-Key` в
   `custom_headers`.
7. **Состояние живого сервера.** Проверка фактического состояния —
   `scripts/compat_check.py`; документ описывает целевой контракт.
